# Contextual Bandit Policy Evaluation Workbench

A reproducible off-policy evaluation (OPE) workbench for estimating the click value of ZOZO's
uniform Random recommendation policy from logs generated by its Bernoulli Thompson Sampling (BTS)
policy. It compares IPS, SNIPS, a Direct Method (DM), and a Doubly Robust (DR) estimator with an
independent Random-policy holdout. A Streamlit dashboard and a small aggregate-only FastAPI let a
reader inspect clipping, support, effective sample size, and test-day variation.

This is a deliberately bounded research exercise. It downloads byte ranges from two large source
CSVs and does not claim that those ranges are a probability sample or represent the full campaign.

## Why this matters

Recommendation and ranking teams often need to estimate a proposed policy before deploying it.
OPE uses outcomes and action propensities logged by an existing policy. This project makes the
trade-offs visible: importance weighting can have high variance, clipping changes the estimator,
and model-based estimates depend on reward-model quality. The independent Random logs provide a
useful held-out benchmark for this dataset, while still being a sampled offline comparison rather
than a production experiment.

## Data and provenance

The source is the [Open Bandit Dataset card](https://huggingface.co/datasets/zozonext/open-bandit),
released by ZOZO NEXT with the
[official data description](https://research.zozo.com/data.html) and the
[Open Bandit Dataset paper](https://arxiv.org/abs/2008.07146). It contains logged fashion
recommendation impressions, action propensities, click outcomes, anonymized user features and
user-item affinity features. The dataset is licensed under
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/); see [NOTICE.md](NOTICE.md) for citation
and attribution.

`data/source_manifest.json` pins the Hugging Face revision, source byte lengths, ETag hashes, and
the deterministic byte-window sampling rule. `make fetch` requests eight 4 MiB ranges from each
policy CSV and retains only complete CSV records. The raw files and derived row-level contributions
stay local and are ignored by Git. Do not redistribute them through this repository.

The resulting local sample contains 65,640 BTS rows and 66,320 Random rows. The ranges span six
shared UTC dates (2019-11-24 and 2019-11-26 through 2019-11-30); 2019-11-25 is absent. The sample
is not the dataset's official small example file and is not probability-sampled.

## Method

1. Use BTS rows from 2019-11-24 and 2019-11-26 to fit reward models.
2. Use BTS rows from 2019-11-27 to choose the reward model by log loss (Brier score breaks ties).
   The comparison is a smoothed item-position CTR baseline and logistic models with three fixed
   regularization values (C = 0.1, 1, 10).
3. On the same validation day, choose among predeclared IPS weight caps by absolute difference to
   the independent Random-policy validation CTR. Ties prefer no clipping.
4. Lock 2019-11-28 through 2019-11-30 for final evaluation. The target action probability is 1/80
   at each position, confirmed by the sampled Random-policy propensities. The learned reward model
   uses item, position, four categorical user features, and the log-transformed affinity between
   the user and the logged item.
5. Compare IPS, self-normalized IPS (SNIPS), DM, and DR with the Random-policy click rate on the
   corresponding held-out dates. Report weight tails, effective sample size, observed
   position-item support, and per-day estimates.

The estimators treat each item-position impression as a decision and assume logged propensities
are correct. They do not model interactions among the three items shown together (slate
interference). The direct model's target value averages its predicted reward over all 80 items for
each observed test context.

## Results from the sampled experiment

The validation comparison selected contextual logistic regression with C = 1: validation log loss
0.03270 and Brier score 0.00521, compared with log loss 0.03398 and Brier score 0.00522 for the
smoothed item-position baseline. The validation rule selected no weight cap: all tested caps had
the same validation IPS point estimate, so the declared tie rule preferred the unclipped estimator.

| Test estimate | Click rate | Absolute gap to Random reference |
| --- | ---: | ---: |
| Independent Random holdout | 0.3049% | — |
| IPS | 0.3636% | 0.0587 percentage points |
| SNIPS | 0.3911% | 0.0862 percentage points |
| Direct Method | 0.3879% | 0.0830 percentage points |
| Doubly Robust | 0.4071% | 0.1022 percentage points |

The locked test split contains 32,764 BTS rows and 33,128 independent Random rows. BTS importance
weights have effective sample size 4,229 (12.9% of the test rows), with a maximum weight of 51.0.
The BTS sample covers 225 of 240 possible position-item cells; the least represented observed cell
has one row. These diagnostics and the roughly 0.06–0.10 percentage-point estimator gaps show that
these estimates should not be treated as a precise campaign-wide policy value.

The intervals in the report use a naive row-independent Wald approximation. They may be too narrow
because impressions can be dependent, and they do not account for the deterministic byte-range
selection. Compare the three test-day estimates and read the limitations in the report and
dashboard. No live deployment effect or causal guarantee is claimed.

## Setup and run

Requirements: Python 3.12 and public Internet access for the bounded data fetch and package
installation. Run these commands from this project directory:

```bash
python3.12 -m venv .venv
make install-lock
make fetch
make validate-data
make train
make evaluate
make test
make quality
make smoke-app
```

To open the interactive dashboard:

```bash
make app
```

Open [http://127.0.0.1:8501](http://127.0.0.1:8501). The weight-cap slider recalculates IPS and
SNIPS and updates clipping and effective-sample-size diagnostics.

The optional aggregate API runs in a separate terminal:

```bash
make api
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/summary
curl 'http://127.0.0.1:8000/estimate?cap=5'
```

Interactive API documentation is at [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).
The API returns aggregate results only; it does not return source rows or hashed user features.

## Tests and local CI

```bash
make test       # estimator formulas and aggregate API behavior
make quality    # Ruff lint and format checks
make smoke-app  # Streamlit render, plots, and clipping-slider interaction; requires fetched/evaluated data
```

The repository includes a GitHub Actions workflow for unit/API tests and Ruff checks. The workflow
does not download the research dataset or run the UI smoke check.

## Repository map

- `src/bandit_ope/data.py` — pinned range download, row-boundary parsing, and source validation.
- `src/bandit_ope/splits.py` — predeclared chronological split.
- `src/bandit_ope/reward.py` — smoothed baseline and contextual logistic reward model.
- `src/bandit_ope/estimators.py` — IPS, SNIPS, DR, and weight diagnostics.
- `src/bandit_ope/train.py` and `evaluate.py` — validation-only selection and locked-test evaluation.
- `app.py` — interactive Streamlit workbench.
- `src/bandit_ope/api.py` — aggregate-only FastAPI endpoints.
- `requirements.lock.txt` — exact Python 3.12 runtime, app, test, lint, and build package versions.
- `reports/` — versioned source/sample and aggregate result manifests; local row contributions are ignored.

## Limitations and next steps

- The byte windows are deterministic and not a probability sample; they do not support unbiased
  extrapolation to the full campaign.
- One campaign date is absent from the sampled windows, and the Random reference windows are not
  exactly time-matched to BTS windows.
- Fifteen position-item cells are absent from the BTS test sample, with sparse coverage in some
  remaining cells.
- OPE assumptions include correct logged propensities, comparable context distributions, and no
  unmodeled slate interference.
- The Random holdout is an offline benchmark. A production decision would need the complete
  licensed data under an appropriate sampling/evaluation design and ideally a controlled online
  experiment.

Potential future work is to validate the conclusions on a principled probability sample or the full
licensed logs, and to evaluate policy and estimator behavior across additional dates and campaigns.
